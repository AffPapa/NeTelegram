# Development build and verification

Use one canonical development bundle across checkouts: `/private/tmp/NeTelegram-Dev.app`. Its default account catalogue is the isolated `/private/tmp/netelegram-dev-support-clean`; set `NETELEGRAM_SUPPORT_ROOT` only when a specifically named QA run needs a separate catalogue. The former `/private/tmp/netelegram-dev-support` is preserved and is not used by routine builds. `Scripts/dev-app.sh` builds intermediates under the repository's ignored `.build/` directory, writes the bundle to the canonical path, and records source and binary fingerprints. It refuses to replace a running NeTelegram process and opens the existing app instance without forcing a second process. The catalogue belongs only to this development app; it is never discovered from an installed Telegram client or shared with a release bundle.

## Test cadence

1. Complete one related vertical slice before rebuilding.
2. Use the lightest check that answers the current question while editing. For Swift source changes, run a focused local test only when it provides fast diagnosis; the full serial suite runs once as the exact-source hosted CI gate. Do not run the same full suite locally and again in CI unless diagnosing a hosted-only failure, validating a toolchain change, or working offline. Do not repeat it when source and harness inputs are unchanged.
3. The hosted macOS suite is the exact-source test gate. Do not use local elapsed time as a hosted-runtime guarantee. Inspect the exact job and decoded logs before retrying. A cancellation after test-binary build but before the first test result is a test-execution failure with unknown test-level cause; diagnose that stage before retrying the unchanged suite. CI runs one filtered deterministic runner probe with a two-minute ceiling before the single full serial suite. Use it to distinguish general runner startup from a suite-specific stall. A versioned `.build` cache is keyed by OS, architecture, Swift/Xcode versions, `Package.swift`, and `TDLIB.lock.json`. Runs 38481765351 (cold) and 38481987804 (warm) both passed the probe and 157-test suite; the measured compile step fell from 48.43s to 17.50s with a 51 MB restored cache. Treat this as a measured result for those runs, not a future cache-hit guarantee. Do not make product-code edits without test-level evidence.
4. Launch the canonical development bundle only for auth, lifecycle, or visible UI changes. Record its build fingerprint and the single scenario checked. Do not use `swift run` to start a second app instance.
5. The macOS unit-test workflow covers `Tests/NeTelegramCoreTests/**`; release metadata Python tests live in `Tests/release/**` and run in the Ubuntu metadata workflow only. Metadata-only test changes therefore do not start another Swift suite. The pinned TDLib/Dev.app workflow is the expensive packaging/lifecycle gate. Push/PR changes to `Package.swift`, `TDLIB.lock.json`, `Scripts/**` native build/lifecycle inputs, and this workflow trigger it automatically. The path names are case-sensitive on GitHub. Source-only Swift changes do not rebuild pinned TDLib; `ci.yml` already runs the serial macOS suite for those changes. Use the existing `workflow_dispatch` for TDLib/runtime integration changes that need a bundled native check and for a frozen release candidate. For visible auth/lifecycle/UI edits, run the single canonical Dev.app scenario only when the changed surface needs GUI evidence. The Ubuntu metadata workflow covers machine-readable checkpoint/template changes.
6. Keep real-account checks separate from synthetic tests. Never seed fake Telegram identities or read installed Telegram app data.
7. Report test count and scenario coverage accurately. A passing synthetic suite does not prove real login, send, multi-account behavior, sleep/wake recovery, or a signed release.

## Fast feedback and release boundary

- One canonical checkout, one source SHA, and one Dev.app path are used for a milestone. Do not switch among stale bundles or rebuild the same candidate after a Site-only failure.
- Docs and static website edits use their relevant validators; metadata edits use `metadata.yml`; Swift changes use the full serial suite once. Native bundle smoke is a separate candidate gate, not another way to rerun unit tests.
- Select checks from the changed paths before editing: Swift source -> one full serial suite; AppKit visible/lifecycle change -> also one scenario in the canonical Dev.app; workflow/toolchain/pin change -> the matching hosted integration gate; state/acceptance/README-only change -> JSON/metadata validators; Site source -> Site build/route checks. Do not rerun an unchanged gate to gain confidence. After a failure, inspect its job/log and change the next action based on the observed failure stage.
- Freeze one release candidate from a clean source SHA. Build/sign/notarize that candidate once, verify its final bytes, publish those immutable bytes, and then update the Site from the verified manifest. Site fixes do not trigger app rebuilds.
- Validate a frozen release candidate with `python3 Scripts/validate_release.py candidate <manifest.json> --assets-dir <frozen-assets-dir>` before publication. After downloading public assets, create a separate receipt and validate it with `python3 Scripts/validate_release.py receipt <manifest.json> <receipt.json>`; never add publication time or downloaded-byte results to the immutable manifest. CI tests these gates with synthetic fixture bytes and cannot substitute those fixtures for real-account coverage.
- Keep each milestone's evidence in `PROJECT-STATE.json`, `ACCEPTANCE.json`, and the append-only `RUN-LOG.md`; never mark a timeout, access denial, or unrun scenario as PASS.
