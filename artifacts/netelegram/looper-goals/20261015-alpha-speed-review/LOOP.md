# NeTelegram alpha speed review

## Outcome

Deliver one trustworthy NeTide 0.1 alpha candidate from one frozen NeTelegram source SHA, with a real one-account login/read/send smoke, separate Developer ID release build, notarization and Gatekeeper evidence, immutable GitHub assets, and one matching public Site update. Keep claims limited to the tested scope.

## Scope and exclusions

- In scope: diagnose repeated workflow errors; keep one canonical checkout, one Dev.app and one release candidate; prove the shortest alpha-critical user path; publish exact verified bytes to GitHub, then update the existing Site once.
- Product requirement at every release: every available authorized account keeps its runtime active; never reduce alpha to one selected account plus a small background subset. Alpha may state an exact incomplete real-account coverage honestly. The 20-real-account/1-5-10-20 resource certification remains open until measured; it is needed before any 20-account performance claim.
- Deferred: channel access until sponsored-media obligations are met; no stable Telegram compatibility claim while §1.3/1.4 and §3.3 remain unresolved.
- Never inspect/import sessions from another Telegram client or expose credentials. Owner performs login only in the app. Do not create a token or open a browser for routine GitHub work.

## Typed acceptance

- Programmatic: source SHA frozen; targeted regression check only for changed code; one exact-source macOS CI; separate release bundle signature verification; notary Accepted plus stapling; quarantine/Gatekeeper install and reopen; immutable GitHub download hashes; anonymous Site download/feed checks.
- Human: owner completes one account login, chat list/read/send/quit smoke in canonical Dev.app; release title and alpha scope remain NeTide, repository codename NeTelegram.
- Judge: visual review only after matching app title, embedded source SHA, PID and fresh screenshot; no style work without a reproduced defect.

## Gates and stop rules

1. Plan gate: refresh exact checkpoint and artifact identities; no implementation while identity differs.
2. Product gate: one real account. Fix only a reproduced alpha-blocking defect; stop architecture-only expansion.
3. Candidate gate: one final source SHA and one exact CI result, then isolated release assembly (never overwrite Dev.app).
4. Distribution gate: notarization and Gatekeeper must actually pass. Missing notary profile is an external blocker; do not bypass it or label the build releasable.
5. Delivery gate: publish immutable GitHub assets and verify public bytes before a single Site update. Site failure does not rebuild or replace app assets.
6. Stop after one diagnosed retry for environment/setup failures; identical second failure requires a changed route or root-cause diagnosis. No repeated CI/build for unchanged inputs.
